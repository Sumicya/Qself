# 04. 项目边界与特性吸收政策

> 2026-09-06 定稿。源自"是否合并 FunBox / XAutoDaily / jhl337.qqhook"的讨论与用户决策。

## 1. 项目定位

hook 型宿主增强模块：被动拦截/增强宿主自身行为。**不模拟协议、不主动自动化、不做定时任务**。
许可证底盘：AGPL-3.0 + 上游 eula；吸收外部代码要求许可证单向兼容（GPL-3.0+/Apache/MIT 可，无许可证不可）。

## 2. 整仓合并的否决理由（原理）

1. 运行形态：协议型/任务型模块（如 XAutoDaily）需要任务调度器+协议客户端+风控对抗，合并=引入新运行时；
2. 风险面改写：自动签到是风控明确靶子，会拉高宿主进程内全部 hook 的整体风险等级；
3. 维护责任转移：原作者活跃的模块（XAutoDaily——LuckyPray 亦为 DexKit 作者）独立存在对本地是净收益；
4. LSPosed 下多模块同方法 hook 为链式组合，共同作用域不构成合并的技术理由。

## 3. 特性级吸收白名单（四条件）

- hook 型（不模拟协议、不主动联网发起业务请求）；
- 许可证兼容且有源码，或无源码但走"知识级重实现"路径（见 §4）；
- 优先 DexKit 型（自愈）；死偏移型慎收；
- 用户有真实使用需求。

## 4. 无源码吸收方法论（androguard 路径）

沙箱已装备 androguard 4.1.4（pip --user）。流程：
1. 取第三方模块 APK；
2. androguard 解析 dex：定位 Xposed 桥调用（findAndHookMethod/hookMethod/DexKit）的类名、方法签名、字符串常量——**这是知识，不受版权保护**；
3. 以本仓端口架构（hostapi/adapter/feature + JVM 测试）从零重实现；
4. 立场：不拷贝其代码/资源；实现独立则功能可自由复刻。
此路径同时是对 RFC-03 抽象的终极检验：吸收一个外部 feature 的边际成本应只有"写一个 adapter"。

## 5. 用户决策记录（2026-09-06）

**FunBox 候选清单（7 项，全部 hook 型，待 APK 分析定 hook 位点）**：
| 功能 | 初步技术画像 |
|---|---|
| 提示伪造随机表情 | NtGrayTipHelper.addLocalJsonGrayTipMsg 直接复用（批 4 能力镜像），成本最低 |
| 防撤回（包围消息提示样式） | 仓内已有 RevokeMsgHook，样式增强 |
| 回复带图 | 宿主消息构造 API 型 |
| 半透明头像上传 | 图片处理 + 上传链路 hook |
| 更详细的群管理 | 群管理页 UI 增强 |
| 群状态日志 | 群成员状态事件监听 + 本地记录 |
| 群组便携菜单 | 群聊 UI 注入 |

**留 FunBox 不吸收**：自动好友点赞、QQ等级加速（主动自动化，白名单外）。
**jhl337.qqhook（底栏液态玻璃）**：源码仓 404；用户需求=角标移至上部居中（嫌默认角标丑）。待 APK 到手分析其角标实现后评估（改派生模块 vs 本仓重实现）。

## 6. 流程备忘

- 第三方 APK 不入公共仓库（即使为分析目的）——只在本地沙箱处理；
- 吸收按既有节奏：一批一 feature、五件套、CI 注解闭环、docs 记账。
