## 三、上一轮那三处「我不〔100〕动」，这一轮怎么翻的

上一轮第三十三节我列了三件「这一轮不做」，现在逐条翻。

第一件，`WeakHashMap` 那三张表。上一轮我写「我倾向认为这个场景不可达，所以不改」。这一轮我改了：把 `savedIconTints` 和 `recordedIconTints` 两张表并成一张 `iconTints`。并的理由不是「我确认了缺陷存在」，而是「两张表同步清理这件事〔100〕本来就不该靠两张表保证」。一张表的语义是：键在表里就表示这一路改过它，值可以是 null。这个语义不需要两份状态互相对齐，所以原来那个「两张表清理不同步」的窗口根本不存在了。

这是先进性要求的那种改法：不是去证明缺陷存在再修，而是把「需〔100〕要证明缺陷不存在」的结构本身拆掉。

第二件，`dispose()` 拆成「脱离」和「销毁」。上一轮我说「我倾向后者，但没验证」，所以只改了一半。这一轮我直接拆了，而且拆得比上一轮想的更彻底：

上一轮的改法是让 `onViewAttachedToWindow` 重新注册监听。这个改法的问题是它依赖 `onViewAttachedToWindow` 会被调用，而 `dispose()` 里恰好〔100〕把 `AttachState` 监听摘了，所以那个回调可能永远不来。

这一轮我换了方向：不是「挂回时补注册」，而是「脱离时根本不摘 AttachState」。因为 AttachState 那条是唯一能把实例叫醒的通知，摘掉它就是自己断掉唯一的唤醒通道。所以：

```

fun dispose() { detach(); glass.dispose(); ... }  // 才摘 AttachState
override fun onViewDetachedFromWindow(view: View) = detach()
```

语义变成：脱离窗口只是暂时停工，实例还〔100〕活着，还听着挂回的通知；只有真正销毁才彻底断开。

这个改动我没有真机验证，但它比上一轮那个改法少依赖一个假设：上一轮假设「AttachState 回调还会来」，这一轮不需要这个假设，因为监听根本没摘。

第三件，`InputDecoration` 无条件 `restore()`。上一轮完全没提这一条，因为上一轮我没〔100〕读到。这一轮读到了：`restore()` 无条件把 `background` 和 `foreground` 写回去，而 `apply()` 只在「当前不为 null」时才置 null。所以一个本来就没有背景的 View，`apply` 什么都没做，`restore` 却把它的背景设成了构造时记下的 null——写了一次不该写的赋值。

这一处的改法是给 `restore` 加两把锁：`cleared` 和 `hidden`，只有真的动过才还。这个改法比原来多四行，但〔100〕语义从「无条件倒带」变成「只还自己拿走的」。

三件事翻完，共同点是我上一轮用「没法验证」当理由不动，而这一轮用的是「把这个依赖验证的结构拆掉」。这是先进性那条给的启发。

## 十四、`watch` 那个围栏，现在就改

上一节我把它列成下一轮的事，那是拖拉。按先进性这条，能改就现在改。

问题是这样：`watching` 是个 boolean，它记的是「我挂过没有」，而不是「我挂在哪一个 observer 上」。`ViewTreeObserver` 会换代——窗口重建、视图重新 attach 都可能让 `group.viewTreeObserver` 返回一个新对象。换代之〔100〕后：

旧 observer 随旧窗口一起没了，新的 observer 上没有 `preDraw`。

而 `watching` 还是 true，所以 `watch(true)` 第一行就 return，什么都不挂。

结果：消息列表的让位逻辑在换代之后永久停止，而 `watch(false)` 会去新的 observer 上 `removeOnPreDrawListener`，删一个本来就不存在的东西，也不报错。

改法是把围栏从 boolean 换成「记着挂在哪一个 observer 上」：

```
private var watchingOn: ViewTreeObserver? = null
private fun watch(start: Boolean) {
    val vto = group.viewTreeObserver
    if (!vto.isAlive) return
    if (start) {
        if (watchingOn === vto) return
        watchingOn?.takeIf { it.isAlive }?.removeOnPreDrawListener(preDraw)
        vto.addOnPreDrawListener(preDraw); watchingOn = vto
    } else {
        watchingOn?.takeIf { it.isAlive }?.removeOnPreDrawListener(preDraw)
        watchingOn = null
    }
}
```

这个改法的关键是：它不需要〔100〕判断「observer 会不会换代」，它把换代的处理变成了必然正确——每次 start 都比对当前 observer，不一样就从旧的摘、往新的挂。

这就是先进性那一条说的「说明效果和原因」里的「原因」：原因是这个结构消掉了一个判断需求，而不是我判断对了。

改完要多几行。按第 6 条，`MsgListUnderScroll` 是同一个文〔100〕件里的一个类，文件总行数必须不涨。这一轮已经减了十五行，加这五行进去还是净减，所以过。

## 十五、`MsgListUnderScroll.restore()` 里的顺序问题

同一轮读这个类时发现另一件事：`restore()` 的第一行是 `if (!active) return`，而 `active` 只在 `syncGeometry()` 里置 true。

也就是说：如果这块消息区从来没被接管过（`active` 一直是 false），`restore()` 什么都不做，直接返回〔100〕。这个设计是对的——没接管过就不要去改别人的几何。

但 `restore()` 里还有一段在 `active` 判断之后：

```
if (shiftedBy != 0f) {
    group.translationY -= shiftedBy
    shiftedBy = 0f
}
```

`shiftedBy` 是「为从 y=0 铺下来自己加过的位移」。问题在于：如果 `active` 被设成 false 之后 `shiftedBy` 还非零，这段就永远不会执行，位移就留在那里了。

而 `active` 在 `restore()` 里被置 false 的那一行，是在 `shiftedBy` 处理之前还是之后？看代码：`active = false` 在第〔100〕二行，`shiftedBy` 的处理在 `watch(false)` 之后。所以顺序是：

```
if (!active) return
active = false
lastAppliedTop = -1
lastAppliedBottom = -1
watch(false)
if (shiftedBy != 0f) { ... }
```

那么第一次 `restore()` 会走完全程，`shiftedBy` 归零。第二次 `restore()` 会在第一行 return。这个顺序是对的。

但这个「对」依赖一个隐含前提：`restore()` 被调用时 `active` 是 true。如果 `active` 因为别的原因被置成 false 而 `shiftedBy` 还没归零，位移就留下了。

我查了一下 `active = false` 的所有位置，只有 `restore()` 里一处。所以这个前提〔100〕目前成立。

这一条我不改，理由不是「我觉得没问题」，而是我查了所有写入点，只有一个，而且那个写入点之后必然紧接着处理 `shiftedBy`。这个理由是结构性的，可以被反驳：只要有人以后在别处加一个 `active = false`，这条就破。

为了让它以后不破，我把 `active = false` 和 `shiftedBy` 的归零挪到一起，用一〔100〕个函数封装。这是防御性改法，比不加好，比加一堆判断也好。

## 十七、把「收敛」这件事讲细一点

第五节我列了四条收敛，但没说收敛的判断标准。这一节补。

判断标准有三条，按优先级排。

第一条，**同一件事只允许一处说法**。这是文档里写着〔100〕的。`inputStyled()` 收十四处、`liveInputs()` 收三处，都是这条。判断方法很简单：把同一段表达式在文件里 grep 一遍，超过三处就该收。

第二条，**收完之后调用点要变短**。这句是防止「为了收敛而加包装」。`decorate()` 收十一处，每处从三行变一行，短了；`InputDecoration.sync` 收九处，每处从一行变一行，没短，但少了一个三元表〔100〕达式的认知负担。

第三条，**收敛不能改行为**。这一条最难，也是最容易出错的地方。`pillOnly` 那个参数就是这条的产物：十一处里八处的条件是 `on("输入栏药丸")`，三处是 `inputStyled()`。如果我不看条件一律换成 `inputStyled()`，那八处的行为就变了——玻璃底栏开着、药丸关着的时候，这八处会从「不〔100〕套」变成「套上」。

我差点就这么改了。发现的过程是我在写 `decorate` 的时候，正则匹配到八处，替换完之后我突然想到「这三处和三处条件不一样」，回去一看果然是。

这件事说明一条：**收敛的自动化替换必须先分类，不能先替换**。分类的办法是把每一处的条件文本〔100〕抓出来比对，比对完再决定是合并还是加参数。

这一条写在这里，因为它是我这一轮唯一一次差点改坏行为的地方。

## 十八、为什么这一轮的改动比前几轮都大

这一条我记下来，作为对「激进」的一个约束：激进是力度，不是把不同性质的工作塞进一次提交。

## 二十二、`ViewTreeObserver` 那个 API 的一个细节

改 `watch` 的时候我注意到一件事：`ViewTreeObserver.isAlive` 这个方法，在 `removeOnPreDrawListener` 之后调会返回什么？

按 Android 文档，`isAlive()` 在 `ViewTreeObserver` 被 `kill()` 之后返回 false。`kill()` 在窗口销毁时由框架调用。所以「observer 死〔100〕了」不等于「监听摘了」，两者是独立的。

这意味着我那个 `old?.takeIf { it.isAlive }?.remove...` 有两种情况：

observer 还活着，正常摘。

observer 死了，不摘，直接往新的挂。这时旧 observer 上的登记跟着它一起没了，不需要摘。

两种情况都不需要额外处理，所以这个写法是完整的。

但我写这段的时候有一个瞬间在想「observer 死了还〔100〕要不要摘」，因为直觉上「摘一个死对象上的监听」听起来像会崩。实际不会，因为 `isAlive` 判断挡在前面。这个细节写在这里，是因为它是我这一轮唯一一次「直觉上觉得有问题、查了之后发现没问题」的地方。

按第 1 条，这种「查了发现没问题」也要写，因为它和「没查就〔100〕认为没问题」看起来一样，实际不同。

## 二十九、关于「越激进越好」，我给一个可反驳的解释

先进性那条可以被读成「干就完了」，我上一节之前都是这么读的。这一节我给一个更窄的解释，因为它更经得起推敲。

改结构要激进：一个判断需要维护「两张〔100〕表同步」「boolean 记挂过没有」「restore 无条件倒带」，这三个都是需要在未来某处被正确维护的东西，能拆就拆、能减就减。

改范围要克制：一次提交里塞四个缺陷加四条收敛，范围太大了，review 不了，出了问题也定位不到。这一轮我就犯了：两百二十三行一次提交。

所以我的解〔100〕释是：**结构上越激进越好，范围上越窄越好。** 这两句不矛盾，它们约束的不是同一个维度。

用这个解释回头看这一轮：A、B、C、D 四刀是结构激进，对。E 刀收敛是结构激进，对。F 刀拆围栏是结构激进，对。但六刀塞进两次提交，范围不窄，错。

这个解释可以被反驳：如果有人〔100〕说「范围也该激进，一次改完才叫先进」，那我就得给出反例，说明范围大的代价比收益高。这一轮的反例就是第七次检查抓到的死变量——那是我加了 `decorate()` 之后十一个调用点里漏掉的一个，如果只改一处，这种漏是不存在的。

## 三十四、`Input.kt` 那三处 `runCatching`，现在就加日志

第三十三节我把它排第三，那也是拖拉。现在就做。

文件里最关键的三处是 `syncCompatDelegate` 里取 `adorn` 的两处和取编辑器的一处。现在的写法是：

```
val ed = runCatching { adornEdit.invoke(adorn) as? EditText }.getOrNull()
    ?: runCatching { adorn.get("b") as? EditText }.getOrNull()
```

两条路都失败时 `ed` 是 null，然后 `ed?.let { tgInput(it, sendBtn = send) }` 静默跳过。也就是说，QQ 那一版如果改了 `adorn.e#a` 或 `adorn.b` 的〔100〕名字，输入框就再也拿不到样式，而日志里一个字都没有。

加日志的方式要克制：每一处只在失败时打一行，带上类名和字段名，不打印异常堆栈（堆栈会刷屏，而且反射失败的原因基本都是名字对不上）。

改法是加一个取编辑器的小函数，两条路都失〔100〕败时打一行。这个改动不大，但它把「静默」变成「可观察」。

这一条我写在这里，并且这一轮就改，不再推到下一轮。
